Zero-Trust Message Lifecycle

How an encrypted message traverses the system with zero cryptographic plaintext exposure to Firebase or cloud relays.

STAGE 01

Sender Client Isolation

Generates an ephemeral 256-bit AES-GCM key in WebCrypto, encrypts message plaintext, and wraps the AES key using the recipient's RSA-OAEP public JWK.

✓ Local IndexedDB Private Key
✓ AES-256-GCM + IV 12-byte
STAGE 02

Zero-Knowledge Relay

Firestore acts strictly as an untrusted ciphertext mailbox. The backend stores Base64 ciphertext, IVs, and encrypted key envelopes without ability to inspect content.

🛡️ Zero Plaintext Stored
🛡️ Realtime Snapshot Stream
STAGE 03

Recipient Local Decrypt

Recipient browser extracts the encrypted key envelope, unwraps the AES session key using their local non-exportable RSA private key, and renders the message.

✓ In-Memory Decryption Only
✓ Decrypted in <2ms
Client Boundary (User Device)

Has access to unencrypted message bodies, local RSA private keys in IndexedDB, live WebRTC camera/microphone feed, and decrypted conversation history.

Cloud & SFU Relay Boundary (Server)

Only sees Base64 encrypted ciphertexts, public RSA JWKs, PBKDF2-salted recovery envelopes, and ephemeral WebRTC media packets.

The Architectural Challenge

Most web messengers sacrifice privacy for real-time responsiveness. Loop was designed to prove that zero-knowledge encryption and low-latency multimedia can coexist without compromises.

Traditional Centralized Messaging

  • Server holds master decryption keys or decrypts messages in transit.
  • Vulnerable to database leaks, provider subpoenas, or server breaches.
  • Passphrase recovery allows providers to reset keys remotely.

Loop Zero-Knowledge Architecture

  • Private keys are generated locally in IndexedDB using W3C Web Crypto API.
  • Zero-Knowledge Server: Firestore only stores JWK public keys & encrypted backups.
  • PBKDF2 + AES-GCM 256 backup using 6-word Diceware recovery phrase.

Key Engineering Decisions & Trade-offs

Real-world architectural trade-offs solved during the implementation of Loop's zero-knowledge stack.

01 • Cryptographic Throughput

Hybrid Encryption Architecture

Problem: RSA-OAEP 2048 cannot encrypt payloads larger than 214 bytes, and pure asymmetric crypto is computationally heavy for long chat histories.

Solution: A hybrid scheme. Loop generates a 256-bit AES-GCM conversation key for lightning-fast hardware-accelerated message encryption, and only uses RSA-OAEP to encrypt/wrap the AES key for recipient peers.

02 • Key Distribution

Zero-Knowledge Key Recovery

Problem: Private keys cannot be stored on cloud servers, but users need a mechanism to restore keys when logging in on a new device or browser profile.

Solution: A 6-word Diceware recovery phrase. Upon signup, PBKDF2 (100,000 rounds, SHA-256) derives an AES master key entirely client-side, encrypting the exported private JWK before saving to Firestore.

03 • WebRTC Scaling

SFU Relays vs P2P Mesh

Problem: Full-mesh WebRTC requires each peer to upload video streams to every other peer ($O(N^2)$ bandwidth), resulting in degraded mobile performance.

Solution: Integrated LiveKit Selective Forwarding Unit (SFU). Each peer only sends 1 upstream track ($O(1)$), allowing the server to forward adaptive bitrates dynamically while preserving sub-100ms latency.

04 • Rendering Performance

Signals-First Change Detection

Problem: High-frequency audio level meters, typing indicators, and message decryption streams trigger continuous global Angular Zone.js dirty-checking.

Solution: Standalone Angular 21 Components powered by Signals. Reactivity operates at the leaf node level, maintaining a locked 60 FPS framerate during live multimedia calls.
